Generated by exploration of the actual codebase. All findings are confirmed by reading source files and querying the live Neon PostgreSQL database.

## Findings Summary

### What is already working
- **Profile text fields** (name, title, department, institution, email, bio, office, office hours) — DB has correct data; PUT `/api/admin/profile` is fully implemented with Zod validation and upsert logic. ✅
- **Academic Links tab** in `/admin/profile` — the page has a complete UI for editing `academicProfiles` JSON and the PUT handler writes it back. The integrations page also has a settings modal that calls `PATCH /api/integrations/update-url` which updates `academicProfiles` in DB. ✅
- **Publications CRUD** — all 14 real publications exist in DB; GET/POST/PUT/DELETE at `/api/admin/publications` are fully implemented and correct. ✅
- **TypeScript compilation** — `npx tsc --noEmit` exits clean (0 errors). ✅
- **Middleware auth** — `/admin` and `/api/admin` routes are protected by `middleware.ts` using iron-session. ✅
- **Photo upload API** — `POST /api/admin/profile` accepts `FormData { photo, slot }`, writes the file to `public/images/`, and calls `prisma.profile.updateMany`. Logic is correct. ✅

### What is broken / needs fixing

#### Issue 1 — All photo `*Url` fields are empty strings in DB
The physical files already exist in `public/images/` (profile.jpg, profile-navbar.jpg, profile-hero.jpg, profile-about.jpg, profile-contact.jpg, profile-footer.jpg, profile-admin.jpg), but the DB columns (`photoUrl`, `navbarPhotoUrl`, etc.) are all `""`. Because the site reads from the DB, photos do not appear on the public site or in the admin sidebar.

**Root cause confirmed:** The photo files were placed manually in `public/images/` but the DB was never updated to point to them.

#### Issue 2 — POST `/api/admin/profile` does NOT check authentication
The GET handler has no auth check (acceptable — it's read-only). The POST (upload) handler reads the session but **does not return 401 if `session.username` is falsy** — it just continues with `performedBy = "admin"`. The DELETE handler does check auth. The PUT handler also does not check auth. This is a security gap — the middleware protects the UI, but a direct API call would succeed unauthenticated.

#### Issue 3 — ORCID and Scopus IDs are placeholders
DB shows `academicProfiles` has:
- ORCID: `https://orcid.org/0000-0000-0000-0000` (placeholder)
- Scopus: `https://www.scopus.com/authid/detail.uri?authorId=0000000000` (placeholder)

These need to be replaced with Dr. Mbita's real IDs. The edit UI works — this is a data entry task via `/admin/profile` → Academic Links tab or `/admin/integrations` → Settings modal.

#### Issue 4 — `ORCID_ID` env var is not set
`/api/admin/sync-publications` (used by the "ORCID Sync" button on `/admin/publications`) reads `process.env.ORCID_ID` and returns a 400 error if missing. The `.env` file has `DATABASE_URL` only — no `ORCID_ID`. The sync button will always fail.

#### Issue 5 — `/api/sync/[platformId]` dynamic route does not exist
`/admin/integrations` calls `fetch('/api/sync/google_scholar', { method: 'POST' })` etc. The `app/api/sync/` directory has named subdirectories (google-scholar, manual, now, trigger, …) but **no dynamic `[platformId]` route**. Clicking "Sync Now" for any platform will get a 404.

#### Issue 6 — `/admin/integrations/page.tsx` double-wraps `AdminLayout`
This page is a `"use client"` component that imports `AdminLayout` and wraps its content with it directly. But the route is under `app/admin/` which already has `app/admin/layout.tsx` as a server layout that renders `AdminLayout`. The result is `AdminLayout` rendered twice — double sidebar, double header. Every other admin page (`publications`, `profile`, etc.) correctly renders only content (no `AdminLayout` import) and relies on the root layout.

## Numbered Fix Plan

- [ ] **1. Seed real photo URLs into the database**

  What is broken: All 7 photo slot columns (`photoUrl`, `navbarPhotoUrl`, `heroPhotoUrl`, `aboutPhotoUrl`, `contactPhotoUrl`, `footerPhotoUrl`, `adminPhotoUrl`) are empty strings in the DB, so photos never appear on the site even though the files exist at `public/images/profile*.jpg`.

  Files to change: Run a one-time Prisma update (can be done via a small Node script or directly in the seed, or via the admin UI upload).

  Correct behavior: Update `prisma.profile.update({ where: { id: 1 }, data: { photoUrl: "/images/profile.jpg", navbarPhotoUrl: "/images/profile-navbar.jpg", heroPhotoUrl: "/images/profile-hero.jpg", aboutPhotoUrl: "/images/profile-about.jpg", contactPhotoUrl: "/images/profile-contact.jpg", footerPhotoUrl: "/images/profile-footer.jpg", adminPhotoUrl: "/images/profile-admin.jpg" } })`.

  Implementation: Add a script `scripts/seed-photos.mjs` that runs the Prisma update and exits. Run it with `node scripts/seed-photos.mjs`. After running, photos should appear on the public site and in the admin sidebar immediately.

  Verify: `node -e "const { PrismaClient } = require('@prisma/client'); const p = new PrismaClient(); p.profile.findFirst({select:{photoUrl:true,navbarPhotoUrl:true}}).then(console.log).finally(()=>p.\$disconnect())"` — should print non-empty URLs.

- [ ] **2. Add auth guard to PUT and POST handlers in `/api/admin/profile/route.ts`**

  What is broken: `PUT /api/admin/profile` and `POST /api/admin/profile` read the session but never return 401 if `session.username` is absent. The middleware guards the UI and `/api/admin/*` paths, but this is defense-in-depth — the handler should also check.

  Files to change: `app/api/admin/profile/route.ts`

  Correct behavior: After getting the session in both PUT and POST, add:
  ```ts
  if (!session.username) return NextResponse.json({ error: "Unauthorized" }, { status: 401 });
  ```
  (identical to what the DELETE handler already does on line 227)

  Verify: With the dev server running, make an unauthenticated `curl -X POST /api/admin/profile` — should return 401. Authenticated requests should still work normally.

- [ ] **3. Fix `/admin/integrations/page.tsx` — remove double `AdminLayout` wrapping**

  What is broken: `app/admin/integrations/page.tsx` is a `"use client"` component that both imports `AdminLayout` and wraps all its return values with `<AdminLayout>`. Because `app/admin/layout.tsx` already wraps every `/admin/*` page with `AdminLayout`, this page renders the sidebar/header twice.

  Files to change: `app/admin/integrations/page.tsx`

  Correct behavior: Remove the `import AdminLayout from '@/components/layout/AdminLayout'` import and remove all `<AdminLayout>` wrapper elements from the two return statements. The content `<div>` inside should be returned directly, exactly like `app/admin/publications/page.tsx` and `app/admin/profile/page.tsx` do.

  Verify: Navigate to `/admin/integrations` — should render a single sidebar and single header, not doubled.

- [ ] **4. Create `/api/sync/[platformId]/route.ts` dynamic route**

  What is broken: `/admin/integrations` page calls `fetch('/api/sync/${platformId}', { method: 'POST' })` for per-platform sync. No dynamic route exists at `app/api/sync/[platformId]/route.ts`, so all "Sync Now" button clicks return 404.

  Files to create: `app/api/sync/[platformId]/route.ts`

  Correct behavior: POST handler reads `params.platformId`, looks up the `profileUrl` from `profile.academicProfiles` for that platform (using the same label map as `update-url/route.ts`), and dispatches sync logic. For `google_scholar` it can call the existing Google Scholar scraper in `lib/scrapers/google-scholar.ts`. For others (orcid, researchgate, scopus, academia, linkedin, github) return a clear JSON response explaining what sync is available. Update `ConnectedAccount.lastSyncedAt` and `syncStatus` after each attempt. Return `{ success: true, count: N }` on success.

  Verify: With a Google Scholar URL set, POST to `/api/sync/google_scholar` should return `{ success: true }` (or a sensible error if the scraper can't reach the URL in the test environment — not a 404).

- [ ] **5. Add `ORCID_ID` to `.env` so the ORCID Sync button works**

  What is broken: `POST /api/admin/sync-publications` returns `{ error: "ORCID_ID not configured" }` when the button is clicked, because `.env` has no `ORCID_ID` variable.

  Files to change: `.env` (add `ORCID_ID=0000-0002-XXXX-XXXX` — replace with Dr. Mbita's real ORCID identifier once confirmed)

  Correct behavior: Once the real ORCID iD is set (the 16-digit format like `0000-0002-1234-5678`), the ORCID Sync button in `/admin/publications` will call `https://pub.orcid.org/v3.0/{ORCID_ID}/works` and import new publications with deduplication.

  Note: This is blocked on Issue 3 (the ORCID profile URL in DB is still placeholder `0000-0000-0000-0000`). Fix issue 3 (update the real ORCID URL via admin UI) and obtain the 16-digit ORCID iD for this env var.

  Verify: After setting `ORCID_ID`, click the "ORCID Sync" button in `/admin/publications` — should return a success message with count, not an error.

- [ ] **6. Update ORCID and Scopus URLs in DB to real IDs**

  What is broken: `academicProfiles` in DB has placeholder values:
  - ORCID: `https://orcid.org/0000-0000-0000-0000`
  - Scopus: `https://www.scopus.com/authid/detail.uri?authorId=0000000000`

  These need to be replaced with Dr. Mbita's actual identifiers so auto-sync, citation tracking, and the public-facing "Find me on ORCID" links work.

  Files to change: No code change needed — use the existing admin UI.

  Steps:
  1. Go to `/admin/profile` → Academic Links tab
  2. Find the ORCID entry, replace URL with `https://orcid.org/<real-id>`
  3. Find the Scopus entry, replace URL with `https://www.scopus.com/authid/detail.uri?authorId=<real-id>`

  Alternatively, use `/admin/integrations` → Settings button on ORCID / Scopus cards.

  Verify: `node -e "const {PrismaClient}=require('@prisma/client');const p=new PrismaClient();p.profile.findFirst({select:{academicProfiles:true}}).then(d=>console.log(JSON.stringify(d.academicProfiles,null,2))).finally(()=>p.\$disconnect())"` — ORCID and Scopus entries should contain real IDs, not zeros.
